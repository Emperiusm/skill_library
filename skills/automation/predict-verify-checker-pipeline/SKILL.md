# Predict-verify-checker pipeline

## Purpose

This skill reconstructs a gated verification workflow end to end, step by step, so another agent can follow the same process. Every phase has three parts: **Do** (the action), **Check** (how the human verifies it), and **Why** (the principle). The core method is: the human predicts first, the worker is blocked from writing or seeing that prediction, an independent deterministic checker recomputes every number from raw exports without trusting anything the worker wrote, the human reviews the checker's redline item by item, and closing the run appends two counts to a learning log, checker errors and human findings. The second count is the one that should grow over time, because it measures the human learning to catch things before the checker does.

The pattern is general. The source domain is architecture, where the pipeline checks area schedules, stairs, panels, drawings, and regulations. The transferable part is the shape of the loop, not the architecture: prediction first, enforced separation, independent recomputation, itemized review, counted learning. It applies anywhere the output has machine-checkable numbers: generated game content with counts and areas, asset budgets, schedules, configuration files, simulation statistics.

## The pattern, and how it differs from its neighbors

Three separations make this pattern, and dropping any one of them collapses it into a weaker loop:

1. **Prediction before work, by the human, enforced.** The prediction is written before the worker touches the task, and the worker is blocked from writing it by any tool, including through the shell. A prediction the worker wrote for itself is not a prediction; it is a guess laundered into authority. The reel's own demonstration has Claude refusing to write it: "The prediction is your own estimate, made before you see the numbers, and a guess from me would defeat that."
2. **The checker is deterministic code, not a second model call.** This is the sharp difference from Anthropic's evaluator-optimizer workflow, where one LLM call generates and another LLM call evaluates (Anthropic, "Building Effective Agents", Dec 19, 2024, https://www.anthropic.com/research/building-effective-agents). An LLM evaluator can work when criteria are clear, but it shares the generator's failure modes. The checker here recomputes from raw exports with arithmetic: shoelace areas from vertices, unit-factor ratios, set membership, string matching against a source text. It cannot be talked out of an answer, and it cannot hallucinate agreement.
3. **Gates are hooks, not instructions.** A rule written in a prompt or a memory file is a request the model usually follows. A hook is code the harness runs every time the event fires, whether the model agrees or not. The five gates below are PreToolUse and Stop hooks with exit-code semantics, not policy text. That is the whole enforcement story, and it is why the pattern survives contact with a model that would rather skip the prediction.

Why not let the model check itself: Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (2024, https://arxiv.org/html/2310.01798v2), found that intrinsic self-correction, a model correcting its own reasoning without external feedback, usually fails and often degrades performance, and that reported improvements in earlier studies came from oracle labels guiding the correction. The checker is the external feedback. The prediction is the human's oracle, written before seeing the answer.

## Tools used

Node.js only, no packages to install (the scripts use only the Node standard library), plus a host that runs hooks: Claude Code with PreToolUse, Stop, and SessionStart hook events. The reference implementation is the Junior Architect Pipeline plugin (install: `/plugin marketplace add abhinavbwj/Junior-Architect-Pipeline`, then `/plugin install junior-architect@junior-architect-marketplace`; or run uninstalled with `claude --plugin-dir ./junior-architect`, then `/junior-architect:setup` in a project folder). The pattern itself needs no Claude Code: any harness with a pre-tool hook that can exit non-zero to block, a stop hook that can refuse completion, and a script runner can host it. What cannot be dropped is the blocking: without a hook that actually refuses the tool call, the gates are wishes.

## Phase 1: Define the task record before any run

**Do**
1. Write one task record per task, in the shape of the reference `pipeline.json` (version 2.0.0). Every record carries: family, stages, autonomy ceiling, agent, skill, checker, the exact check command with its inputs, deliverable filename, inputs, the judgement step the junior keeps (`junior_keeps`), failure modes, hosts, and capabilities the host must provide (described in plain words, so any tool that provides them can be used).
2. Write the failure modes first, before the happy path. The reference records name concrete ones per task: "dropped requirement", "invented requirement", "requirement paraphrased into a different meaning" (brief digest); "model not georeferenced", "true north and project north confused", "terrain from a coarse dataset presented as survey" (site model); "rule entered without a source clause", "compliance claimed from an unchecked number" (regulation check). A task with no named failure modes has no checker worth writing, because nobody has said what the checker is for.
3. Write the `junior_keeps` line as a concrete pre-work act, not a vague "review". Reference examples: "Before reading the digest, rank the three requirements that will drive the plan and say why." "Predict the maximum gross floor area the envelope allows before the model computes it." "Name the rule you expect the design to fail, and by how much." If the junior's kept judgement cannot be written as one sentence naming what they do before the work, the task is not ready.
4. Put the project standards in one file the checker reads, `.jap/project.json` in the reference: units, area definition, naming conventions, status codes, tolerances, rule limits. The checker reads limits from this file, never from the worker's output. A limit the worker supplied is not a limit.

**Check**
- Every task record has a checker whose name exists in the checker registry, a deliverable filename, and at least one named failure mode. A record missing any of the three is incomplete.
- The ceiling for the task is set deliberately (see Phase 2). No task defaults to fully automatic.

**Why**
- The task record is the contract the gates enforce. Hooks and checkers read it; the worker does not get to renegotiate it mid-run. Writing it down before any run is what makes "the checker recomputes" a checkable claim instead of a slogan.

## Phase 2: Set the autonomy ceiling per task

**Do**
1. Assign one of five ceilings, using the reference definitions verbatim in meaning:
   - **A0:** The junior does the task. The agent stays silent unless asked a question.
   - **A1:** The agent drafts only after the junior has written a prediction. The junior rewrites or approves every line.
   - **A2:** The agent executes. Deterministic checks gate the output. The junior reviews the redline and accepts or rejects each item with a reason.
   - **A3:** The agent executes and checks. The junior signs off a sample of at least 20% of items.
   - **A4:** Fully automatic. Not used for any task in the reference map by default.
2. Cap the run at the ceiling in code, not in prose. The reference `start()` function caps a requested autonomy above the ceiling down to the ceiling and says so: "autonomy A3 exceeds the ceiling for area-schedule; capped at A2". A ceiling the worker can talk its way past is not a ceiling.
3. Derive the run's requirements from the ceiling: prediction required at A1 and A2; review required at A1, A2, and A3. At A0 there is no run to gate; at A4 there is no human in the loop, so A4 must be a deliberate, recorded decision per task, never a default.

**Check**
- For the task you are about to run, state the ceiling, whether a prediction is required, and whether a review is required, before opening the run. If you cannot state all three, the task record is incomplete.

**Why**
- Autonomy is the blast radius. The ceiling decides how much unverified work can exist before a human looks at it, and the prediction and review requirements follow from it mechanically. Deciding the ceiling per task, in advance, is what stops a routine task from silently running at full autonomy because nobody set the dial.

## Phase 3: Open the run and record the prediction first

**Do**
1. Open the run with a single command that creates the run state and refuses to proceed while another run is open. The reference: `jap start <task> [A0-A4]`, which writes `.jap/state.json` and `.jap/runs/<date>-<task>-<nn>/run.json`, and dies with "run X is still open; close it first" if a run is already open. One open run at a time is a feature: it makes the state file a single source of truth the hooks can read.
2. The junior records the prediction themselves, out of band, with the pipeline CLI: `jap predict "<estimate>"`. In the reference demo the prediction names a total and the three largest deviations from the brief: `node "C:\JAP\junior-architect\scripts\jap.js" predict "total = ... m2; largest deviations: 1) room ...; 2) ...; 3) room ..."`. The Windows path is the creator's local install; the repo's entry point is `junior-architect/scripts/jap.js`. A rough gut call is acceptable and explicitly encouraged ("It takes about ten seconds. A rough gut call is fine."). Precision is not the point; commitment before seeing the numbers is.
3. Let the hooks enforce the order. At A1 and A2, before `prediction.md` exists in the run folder, the PreToolUse gate blocks every MCP call and every write into the run folder, with the message "Prediction first ... The junior records a prediction before the agent works ... Then retry." The worker cannot start early, cannot peek at the model to calibrate its guess, and cannot write a prediction for the junior.
4. The prediction file is append-only through the CLI (`fs.appendFileSync` with a timestamp). The worker cannot edit it, overwrite it, or delete it: the gate blocks Write, Edit, and MultiEdit to `prediction.md` and `review.md`, and blocks the shell from writing them through the CLI (`jap.js predict|review` invoked through Bash is blocked) or by redirection, copy, move, remove, or in-place edit of any evidence file.

**Check**
- Before the worker acts, `prediction.md` exists in the run folder, written by the junior, and names at least one number plus the largest expected deviations. A prediction that says only "looks fine" fails this check: it names nothing to compare against.
- Attempting to write the prediction through the worker's tools is refused. If it succeeds, the gates are not installed, and nothing downstream can be trusted.

**Why**
- The prediction is the only part of the run the worker cannot influence, which is exactly why it is useful. It converts review from "does this look right" into "where does this differ from what I expected, and is the difference explained". The ten seconds it costs buys the only independent expectation in the whole loop.

## Phase 4: The worker executes through tools only, inside its isolation

**Do**
1. Give the worker only the tools its job needs. The reference has 17 specialist subagents, each scoped to its task's tools, and each task record lists the host capabilities required. Isolation is a separate layer from the gates: the gates police the evidence files, isolation limits what the worker can touch at all.
2. The worker does the task through the host's tools (MCP servers in the reference: Rhino, Grasshopper, Revit, Archicad, SketchUp, Blender) or, without a connected server, from exported files. The reference is explicit that tasks also run on exported files; the MCP server is a convenience, not a requirement. What matters is that the worker's output lands as raw exports the checker can read, not as prose claims about what the output contains.
3. The worker must not present any number as confirmed. The Stop gate enforces this at the end (Phase 6), but the discipline starts here: numbers the worker states in chat are drafts until the checker has recomputed them.

**Check**
- The worker's output exists as files the checker is about to read (exports, schedules, geometry), not only as chat text. If the only record of the result is something the worker said, there is nothing to check.
- The worker used no tool outside its task's capability list. A capability used but not listed is a scope breach, even if the result looks fine.

**Why**
- Isolation keeps the blast radius small and the checker honest. A worker with write access to the evidence files, the checker code, or the learning log can manufacture a pass; the gates in Phase 6 exist because isolation alone is never airtight, but isolation is what makes the gates cheap to enforce.

## Phase 5: The independent checker recomputes from raw exports

**Do**
1. Run the task's checker as a separate command that takes raw inputs and writes the only report: `jap check [inputs...]`. The reference `check()` function looks up the checker by name from the run state, runs it, and writes `.jap/runs/<run>/report.json` with run, task, checker, inputs, timestamp, pass/fail status, error and warning counts, metrics, and the full issue list. Only this command writes the report; the gate blocks every other write path to it (G2).
2. Write each checker as a pure recomputation from raw data. The checker reads the raw export, recomputes the quantity from first principles, and compares. It never reads the worker's summary, never trusts a number the worker wrote, and never calls the model. The reference header states the rule in one line: "Every checker recomputes from raw data. None of them trusts a number the agent wrote."
3. Return issues in a fixed shape: `{level, code, item, detail}` with level `error` or `warn`, plus a metrics object (counts and totals). The fixed shape is what makes reports comparable across runs and lets the close step count errors mechanically.
4. Build checkers from these verified patterns in the reference code. Each is a real function read firsthand; use them as templates, not as metaphors:
   - **Recompute geometry from vertices (check_areas).** Read room polygons and targets. Convert units with an explicit table (mm, cm, m, ft, in). Reject open boundaries ("boundary curve is open: area undefined") and polygons with fewer than 3 vertices. Recompute area with the shoelace formula. Flag self-intersecting boundaries, wrong layers, and boundaries drawn to the wrong definition (for example centreline when the project measures the inner face). If a reported area is present, flag it when it differs from the recomputed area by more than 0.5%. Detect duplicates (same area within 0.1% with vertices within 0.01) and nesting (every vertex of the smaller polygon inside the larger: "room lies inside another room: counted twice unless deducted"). Match names to targets with Levenshtein distance 2 or less and report "did you mean" on typos instead of silently dropping the room. Flag deviation from target beyond the project tolerance (default 5%).
   - **Unit-trap detection (check_areas).** An area off from its target by a units factor is a units error, whatever else it looks like. The reference tests eight ratios with an 8% match window: 10.7639 (square feet read as square metres), its reciprocal, 1e6 and 1e-6 (millimetre/metre coordinate confusion), 1/92903.04 and 92903.04 (feet/millimetre), 1/0.09290304 and 0.09290304 (feet/metre). The demo's feet-drawn flat shows up as ratio 0.00001076 in the log. Generalize the pattern: whenever a measured value and its target differ by a known conversion factor, report the factor and the probable confusion instead of a bare deviation.
   - **Two-sided set reconciliation (check_schedule).** Compare a schedule against a model export in both directions: duplicate marks in the schedule, items in the model but not the schedule, items in the schedule but not the model ("stale schedule?"), empty required fields, and value mismatches field by field after normalization. In audit mode, also surface model-health flags the export carries.
   - **Verbatim traceability (check_trace, check_clauses).** Every requirement or cited clause must carry a verbatim quote, and the quote must appear in the source text after normalization. A requirement with no quote is an error ("untraced"); a quote not found verbatim is an error ("quote-not-in-source"). Clause notes must carry Clause, Edition, Jurisdiction, and Quote fields, and the quote must appear in the supplied code documents or the entry is unverified. Paraphrase that changes a threshold is the failure mode this exists to catch.
   - **Register discipline (check_sheets, check_refs).** Duplicate numbers, naming-pattern violations, status codes outside the office list, dead references to items not in the register, superseded revisions cited when a newer revision is current, and self-checking (drawn_by and checked_by the same person). A document that references a revision that no longer exists is an error, not a warning.
   - **Rules with sources (check_metrics).** Compare measured values against rules with operators (<=, >=, <, >, ==, between, within with a tolerance percentage, default 5%). Every rule should carry a source; a rule without one warns: "a limit without a clause cannot be defended". A limit nobody can source is not a limit.
   - **Domain rules from first principles (check_stairs, check_panels, check_gh).** Stairs: Blondel 2R+G within 550 to 700 mm, riser and going limits, clear width, headroom, pitch, maximum risers per flight, total rise equal to floor-to-floor within 3 mm, riser variation within a flight under 5 mm; limits come from the project file, with placeholder defaults that warn loudly ("checked against placeholder limits: set stair_rules from your code"). Panels: fabrication size limits, stock-sheet fit in either orientation, planarity, and a type budget. Grasshopper definitions: components in error or warning state, required inputs with no source and no data, unnamed sliders ("slider has no name: nobody can read the definition"), internalised geometry that no longer follows the model. The pattern in all three: limits from the project file, recomputation from the export, and a warning whenever a placeholder stands in for a real standard.
5. Keep checkers dependency-free and fast. The reference scripts are Node only with no packages, because a checker that needs installing is a checker that will not run. A checker should run in seconds on the run's inputs and print one line per issue plus a metrics summary, so the human can read the whole report at a glance.

**Check**
- The report exists at `.jap/runs/<run>/report.json`, written by the check command, with a pass/fail status and a metrics object. No report, no close (Phase 6 refuses).
- Every number in the deliverable that the worker produced appears in the report as either confirmed by recomputation or flagged. A number that appears nowhere in the report is an unconfirmed number, and presenting it as confirmed is exactly what gate G4 blocks.
- The checker read raw exports, not the worker's summary. If the checker's inputs are the worker's chat output or a file the worker wrote as its conclusion, the separation is broken: re-point the checker at the raw export.

**Why**
- Recomputation is the only verification that does not share the worker's assumptions. A second model reading the worker's output can repeat the worker's mistake with confidence; arithmetic on the raw export cannot. The unit-trap pattern is the proof: a model sees "62.60 against 66" and calls it a small deviation, while the checker sees the ratio 0.00001076 and names the units error.

## Phase 6: Redline review and close with the two-count log

**Do**
1. The worker presents the redline: the checker's issues, item by item, against the human's prediction. In the reference demo the worker says: "Your prediction was about 2,400 m2, with the 4R flats as the worst and one 2R under target. For each item above, accept or reject it with a reason."
2. The junior reviews the redline and records it themselves: `jap review "<accept/reject each item, with reasons; found: ...>"`. The review must accept or reject each item with a reason, and must add anything the checker missed, prefixed `found:`, comparing the result with their own prediction. The `found:` prefix is load-bearing: it is how the close step counts junior findings (see step 4). The gate blocks the worker from writing the review by every path, exactly as with the prediction.
3. If a second pass is wanted, fix the issues, re-export, and re-run the schedule and checker before closing. The run stays open until closed, and the checker can be re-run on fresh inputs; each run produces one report, and close refuses without one.
4. Close the run: `jap close`. Close enforces, in order: a checker report exists; a prediction exists if the ceiling requires one; a review exists if the ceiling requires one. Then it appends one line to `learning_log.csv` (header: `date,task,autonomy,run,checker_errors,junior_findings,prediction_note`) with the report's error count and the junior-findings count, which is the number of lines in the review starting with `found:`, `missed by checker:`, or `extra:`. It deletes the open-run state file. The reference close message is the whole philosophy in one line: "Closed 2026-11-19-area-schedule-01. Logged: checker errors 14, junior findings 1."
5. Read the learning log as a trend, not a score. The reference `log` command prints one line per run: date, task, autonomy, checker errors, junior findings. The stated goal is that junior findings grow over time: the junior learns to catch things before the checker. A falling junior-findings count with a steady checker-error count means the junior is deferring to the checker; a rising checker-error count means the work is getting worse or the checker is getting stricter, and the two need separating before anyone celebrates.

**Check**
- `close` refuses when any required artifact is missing. If it succeeds without a report, a prediction, or a review that the ceiling requires, the enforcement is broken.
- The learning log gained exactly one line for the run, with the correct error count from the report and the findings count from the review's `found:` lines. A log line written by anything other than the close command is suspect: the gate blocks all other write paths to it (G2).
- The review names an accept or reject with a reason for each redline item. A blanket "accepted" with no per-item reasons is a rubber stamp, and the close step cannot detect it, which is why the review format requires per-item reasons as a human discipline, not just a file.

**Why**
- The review is where the human's judgement enters the record, and the log is where judgement becomes a trend. Without the per-item review, the checker is an oracle nobody interrogates; without the two counts, nobody can tell whether the human is learning or atrophying. The counts are deliberately asymmetric: checker errors measure the work, junior findings measure the human, and only the second is supposed to grow.

## Phase 7: Prove the checker with planted faults before trusting it

**Do**
1. Build a seeded-fault test set: one example input per fault the checker claims to catch, each seeded with exactly one known fault, plus clean examples that must pass. The reference README claims `node junior-architect/tests/examples.test.js` runs all 20 checkers on seeded-fault examples and asserts exactly which faults each one reports, with all 20 cases passing. That test file was not read firsthand in this session, so treat the claim as the README's; the method, however, is directly visible in the checker code and is what this phase prescribes.
2. Assert exact fault identity, not just pass/fail. For each seeded example, assert the checker reports the specific fault code for the seeded fault (for example `unit-trap`, `open-boundary`, `duplicate`, `nested`, `blondel`, `self-checked`) and no others. A checker that reports "something is wrong" without naming the fault has not proven it understands the fault.
3. Seed the faults from the task's own failure-mode list (Phase 1), one per mode, plus the classic traps: a units confusion, a duplicate, a nested item, a stale reference, a paraphrase that changes a threshold, a self-check. The reference demo's planted set is the template: a flat drawn in feet, a boundary left open, a store counted twice, a flat measured to the centreline. The checker found all ten planted faults plus four the planters had not listed, which is the strongest possible result: the test set proved the checker catches more than the test set contains.
4. Re-run the seeded set whenever the checker, the project standards, or the input format changes. A checker that passed last month against last month's format proves nothing about this month's export.

**Check**
- Every checker in the registry has at least one seeded fault it is asserted to catch, and the suite passes with exact fault codes. A checker with no seeded test is an unproven checker: do not gate a run on it.
- The suite includes clean examples that pass. A checker that flags everything proves nothing either; it must discriminate.

**Why**
- A checker is itself code, and code that has never been shown to fail on a known fault is a claim, not a control. Planted faults are the only honest proof available, because they convert "the checker works" from a belief into a demonstration with a known answer. The demo's extra four catches are the point: a proven checker finds faults nobody planted, which is the only reason to trust it on faults nobody imagined.

## The human method, distilled

The creator's method, as demonstrated in the reel and implemented in the code, in five moves: (1) the junior commits to an expectation before seeing any numbers, in writing, in their own words; (2) the worker is physically prevented from writing, seeing, or editing that expectation; (3) the work is done through tools that produce raw exports; (4) a separate deterministic program recomputes every number from those exports and writes the only report; (5) the junior interrogates the report item by item, records what the checker missed, and closes the run into a log that makes learning visible. Everything else, the 45 tasks, the 17 subagents, the MCP servers, is scaffolding around those five moves. When adapting the pattern, keep the five moves and feel free to discard the scaffolding.

## The five gates, verbatim in effect

From the reference README and `gate.js`, read firsthand. G1: Claude cannot write the junior's prediction or review, by any tool, including the CLI through the shell. G2: only the checker writes the report, the run state, and the learning log. G3: at A1 and A2, no MCP call and no write into the run before the prediction. G4: Claude cannot finish while a deliverable has no checker report. G5: checkers and gates are read-only during a run. The gates act only in projects with a `.jap/` folder, and only while a run is open, except G1 and G2, which act whenever the folder exists. The junior's own prediction command runs outside the model's tools (the `!` escape in Claude Code), so the hooks never see it, which is the deliberate hole that makes the whole thing usable: the human acts outside the harness, the model acts inside it.

## Failure modes

1. **The worker writes the prediction.** The gate blocks Write, Edit, MultiEdit, and the shell paths to the prediction and review files, including redirection, copy, move, remove, and in-place edit of evidence files. If a prediction appears in the worker's words, the gates are not installed: stop and install them before trusting anything.
2. **The checker reads the worker's conclusion.** Re-point the checker at raw exports. If the raw export does not exist, the task is not checkable yet: produce the export first, then check.
3. **Checker and worker share assumptions.** The checker must use a different method from the worker: shoelace from vertices, not the modelling tool's area function; string matching against the source text, not the worker's digest. Planted faults (Phase 7) are the test that catches shared blind spots.
4. **The prediction is too vague to compare.** Require a number and the largest expected deviations. "Looks fine" is not a prediction; it is permission.
5. **The review is a rubber stamp.** Require accept or reject per item with a reason. The close step cannot detect a blanket acceptance, so this one stays a human discipline enforced by format, not by code.
6. **The learning log is gamed.** Findings count only from `found:` lines, and the trend is reviewed, never rewarded per run. A junior who invents findings to grow the count is falsifying the record; the review text is the audit trail.
7. **Autonomy creep.** The ceiling is capped in code at run open. If a run's autonomy exceeds its task ceiling, the cap code is bypassed or absent: fix the cap, do not argue with the worker.
8. **Gates bypassed by editing the plugin.** G5 makes checker and gate files read-only during a run, and the gate blocks writes under the plugin directory. Keep the plugin directory outside the worker's write scope permanently, not just during runs.
9. **Deliverable without a report.** The Stop gate blocks finishing when a deliverable exists but no report does, with the reason "Never present a number the checker has not confirmed." If finishing succeeds in that state, the Stop hook is not wired.
10. **Tolerance laundering.** Tolerances and limits live in the project standards file, set by a named senior (the reference requires a senior to set `area_standard`). Changes to the standards file are themselves reviewed: widening a tolerance to pass is falsifying the check, and it must be as visible as any other evidence change.
11. **An untested checker gates a run.** No seeded-fault proof, no gate. A checker that has never been shown to fail on a known fault is a claim, not a control (Phase 7).
12. **The checker checks the wrong file.** The check command names its inputs explicitly in the task record. If the inputs are ambiguous ("the latest export"), the checker may confirm a stale file while the deliverable changed. Name inputs, never glob them.

## AAA studio practice

The reference implementation is a solo architect's plugin, not a studio system, so the studio practice below is drawn from published agent and verification work read firsthand, and is labeled as secondary support. The repo code is the primary source; this section explains why its shape matches what the field converged on.

**Evaluator-optimizer, with a deterministic evaluator.** Anthropic's "Building Effective Agents" (Dec 19, 2024, https://www.anthropic.com/research/building-effective-agents) describes the evaluator-optimizer workflow: one LLM call generates a response while another provides evaluation and feedback in a loop, effective when evaluation criteria are clear and iterative refinement provides measurable value. The Junior Architect Pipeline is that workflow with the evaluator replaced by code: the generator is the worker, the evaluator is the checker, and the loop is the redline review. The replacement matters. An LLM evaluator shares the generator's training, its blind spots, and its tendency to agree; a deterministic checker shares none of them. Use an LLM evaluator when the criterion is taste, clarity, or style. Use a deterministic checker whenever the criterion is arithmetic, membership, or verbatim presence, which is every case this skill covers.

**Intrinsic self-correction fails; external feedback is the fix.** Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (2024, https://arxiv.org/html/2310.01798v2), found that models asked to correct their own reasoning without external feedback usually fail and often get worse, and that earlier reported improvements depended on oracle labels guiding the correction. The prediction is the human's oracle, written before the answer exists. The checker is the external feedback. The pattern's two external anchors are not decoration; they are the entire reason the loop improves instead of degrading. Any variant that drops either anchor and keeps the loop is re-running the experiment Huang et al. already ran, with the same expected result.

**Enforcement is hooks, not prose.** Claude Code hook field notes checked against the Hooks reference in November 2026 (https://futurecraft.pro/blog/claude-code-hooks/) confirm the semantics the reference gates rely on: exit code 2 from a PreToolUse hook blocks the tool call and shows stderr to the model, while exit 1 is a non-blocking error that lets the call run; a Stop hook returns a block decision to keep the model working, and must respect the `stop_hook_active` flag or it loops. The reference `gate.js` implements exactly this: exit 2 with stderr for PreToolUse blocks, a `{"decision":"block"}` JSON answer for the Stop event, and an early exit when `stop_hook_active` is set. The lesson generalizes beyond Claude Code: a policy that lives in a prompt is a request; a policy that lives in a hook with blocking semantics is a control. If your harness cannot block, say so plainly and do not claim the gates hold.

**The harness doctrine, stated plainly.** Quality is a deterministic gate, not a request. Memory files and rules are advisory context; hooks, gate scripts, and CI are the enforcement. The reference implementation embodies this in miniature: the task record, the gates, and the checker are code and config the worker cannot rewrite mid-run, and the learning log is the audit trail that makes the whole thing reviewable after the fact.

## Agent automation

An agent building or running this pipeline should enforce these gates mechanically. Each gate names what it checks and what it refuses:

1. **Task-record gate.** Before opening a run, verify the task record has a checker name present in the registry, a deliverable filename, at least one named failure mode, and a `junior_keeps` sentence naming a pre-work act. Refuse to open the run if any is missing.
2. **Ceiling gate.** At run open, cap requested autonomy at the task ceiling and log the cap when it bites. Refuse A4 unless the task record explicitly allows it and the decision is recorded.
3. **Prediction-presence gate.** Before any worker tool call at A1/A2, verify `prediction.md` exists in the run folder and names at least one number. This is the G3 check, re-implemented as a pre-flight the agent runs itself in harnesses without hooks.
4. **Checker-test gate.** Before a checker gates its first real run, run its seeded-fault suite and require exact fault-code matches plus clean passes. Refuse to gate on an unproven checker.
5. **Report-presence gate.** Before presenting any number from a run, verify `report.json` exists and its status is pass, or present the failures alongside the number. Never present an unconfirmed number as confirmed.
6. **Evidence-write gate.** Verify that only the pipeline CLI wrote `report.json`, `state.json`, `run.json`, and `learning_log.csv` (file ownership or append-only handling per harness). Any other writer invalidates the run: close it without logging and start over.
7. **Learning-log gate.** At close, verify exactly one line was appended, with the error count from the report and the findings count from the review's `found:` lines. Verify the prediction note is the first 120 characters of the prediction with commas replaced, matching the reference close behavior, so the log stays parseable.
8. **Tolerance-change flag.** Any change to the project standards file (tolerances, limits, area standard) between runs must be flagged in the next run's review. Tolerances are evidence, not settings.

## Valkyrie note

Valkyrie is a Godot 4.7.2 C# god game with an authored Pellune Island map, deterministic seeded scatter on authored masks, a fixed isometric camera, and a wallpaper bar. The pattern transfers directly to procedural generation work, which is where Valkyrie most needs it:

**Worked example, procedural district generation.** A generator proposes a district: building footprints, a claimed building count, a claimed total floor area, and a claimed courtyard sun share. The checker recomputes from the placement records, never from the generator's claims: recount buildings from the placed-instances list; recompute each footprint area with the shoelace formula from its vertices; convert units with an explicit table and flag unit-factor ratios (a district laid out in centimetres read as metres shows up as a 1e4 area ratio, the same shape as the reference unit trap); flag duplicate footprints and nested buildings; compare each area against the brief targets with the project tolerance; flag any building whose claimed area differs from its recomputed area by more than 0.5%. The human predicts the building count, the total area, and the worst deviation before the generation runs. The review accepts or rejects each flagged building with a reason. Close logs checker errors and human findings. The planted-fault proof: seed a district with one centimetre/metre confusion, one duplicated building, one nested courtyard building, and one footprint drawn to the wrong boundary definition, and require the checker to name all four codes exactly.

The same shape covers simulation statistics (recompute citizen counts, resource totals, and pathing costs from sim logs rather than trusting the sim's own summary), asset budgets (recompute triangle counts and texture memory from the exported files, not the exporter's log), and scatter placement (recompute instance counts and mask coverage from the placed data). Honest limit: this environment has no Claude Code hook host, so the live hook blocking in the reference cannot run here as written. What transfers fully is the deterministic checker, the prediction discipline, the two-count log, and the planted-fault proof; the enforcement layer in this environment is the agent running the pre-flight gates above plus CI, not a live PreToolUse hook. Do not claim hook enforcement where no hook host exists.
