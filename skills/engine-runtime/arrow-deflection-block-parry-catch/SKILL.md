# Arrow deflection: block, bounce, catch, slash

## Purpose

This skill builds a defensive system for incoming projectiles end to end, step by step, so another agent can follow the same process. Every phase has three parts: **Do** (the action), **Check** (how the human verifies it), and **Why** (the principle). The core method is: the design history is the spec. A four-month public thread took this mechanic from a viewer suggestion, through a collision bug, to a voted verdict and a deliberate decision to keep it hidden, and this skill implements exactly what that thread decided, with the parts the thread never settled labeled as this skill's own design.

Two things this skill is not. It is not the sibling gating skill: `engine-runtime/forward-trace-melee-attack-gating` covers stopping a swing when a wall is in the way; this skill covers what happens when an arrow meets a raised sword. And it is not the sibling projectile skill: `engine-runtime/scripted-thrown-weapon-projectile` covers authoring a thrown weapon's flight; this skill covers intercepting someone else's projectile. Cross-links to both appear where the work overlaps instead of re-teaching it.

## Block, parry, catch, slash: pick the outcomes

Four outcomes, one input family, different timing and cost. Do not build all four at once; the thread's own order is the build order (block first, bounce second, catch and slash third).

- **Block.** Holding the guard. Any arrow entering the guard volume is stopped: it bounces off with sparks (the Oct 25 verdict) or drops. No timing required, no reward beyond survival. This is the shipped baseline the thread voted on.
- **Parry.** A fresh press inside a short window just before impact. Same interception, better reward: a stronger redirect (the arrow flies back toward the shooter or away at speed), a bigger feedback spike, and optionally a stagger or opening on the archer. The timing window is the skill; see Phase 3.
- **Catch.** Proposed Jul 11, endorsed, never shown. The arrow is caught mid-flight and kept: it becomes ammunition or simply disappears into the hand. The catch must be visibly different from a block (a grab animation or hand snap, not a bounce), or players cannot tell which one happened.
- **Slash.** Proposed Jul 11, endorsed, never shown. An attack swing meets the arrow mid-flight and cuts it: the arrow splits (two halves with physics fall, per Greyson Loomis's unendorsed visual) or despawns with a spark. The slash uses the attack's active frames, not a guard volume; see Phase 4.

## Phase 1: Write the verdicts down before building anything

**Do**
1. Copy the four dated verdicts from the Source section into the feature's design note, with their dates: catch endorsed (Jul 11), slash endorsed (Jul 11), bounce-off-with-sparks decided (Oct 25), keep-it-hidden decided (Oct 25).
2. Write the non-verdicts in a separate list marked "proposed, not decided": stamina cost, progression gating, ammo reuse, physics-fall, slice-in-half visual. Each one needs its own decision before it is built; none of them inherits the Oct 25 verdict.
3. Decide which outcomes this build ships, in the thread's order. The recommended first build is block plus bounce only: it is the entire Oct 25 verdict, and it is testable without any timing system. Parry, catch, and slash are second-build features with their own phases below.
4. Decide the hidden-mechanic rule now, because it constrains everything else (Phase 6): the mechanic is discoverable in play but never explained in a tutorial, tooltip, or loading screen. That is the creator's decision, and it means feedback must teach it alone.

**Check**
- The design note quotes the creator's verdicts with dates, and the unendorsed list is visibly separate. If a proposed idea has drifted into the "decided" column, the note is wrong and the build will overreach.
- The first build's scope is block plus bounce only, or the scope document says explicitly which later outcomes are included and why.

**Why**
- The thread is unusually well documented for a community design process, and the most common failure in rebuilding it is treating every liked comment as a decision. The like counts are not votes: the creator's replies are the decisions. Keeping the two lists separate is what stops a 346-like suggestion from becoming a requirement and a 4-like suggestion from being ignored when the creator endorsed it.

## Phase 2: The guard volume that intercepts arrows

**Do**
1. Build the guard volume as an `Area3D` child of the player (or of the citizen, in third person), positioned in front of the raised sword, sized to the blade plus a hand's width. It is a detection region, not a physical barrier: Area3D "detects when other CollisionObject3Ds enter or exit it" and "does not act as a physical barrier". The arrow never collides with the volume; the volume reports the arrow, and the script decides the outcome.
2. Set the layers so the volume sees arrows and nothing else. The arrow is an Area3D or body on its own layer (call it `projectile`); the guard volume's mask includes `projectile` only. The arrow's mask must include whatever the guard volume sits on only if the arrow also needs to detect the volume; in the standard setup the volume is the seer (monitoring true) and the arrow is the seen (monitorable true), and the signal is `area_entered` for area-to-area pairs, `body_entered` for body arrows. Both flags default to true; the failure mode is turning one off while debugging something else and forgetting it.
3. Give the arrow a stable identity the volume can read: the arrow's root script exposes a method such as `get_flight_velocity()` and a flag such as `is_deflectable`. Unblockable arrows (the Sekiro perilous category, the Tsushima red-glint category) carry `is_deflectable == false` and pass through the volume untouched. The volume never decides deflectability from the arrow's name or scene path.
4. Handle the transition-only rule explicitly. Area signals fire on overlap transitions: an arrow that spawns already overlapping the volume (point-blank archer, or the volume enabled while an arrow is inside it) fires no signal. On enabling the volume, call `get_overlapping_areas()` (and `get_overlapping_bodies()` for body arrows) once and resolve anything already inside, or accept that point-blank arrows cannot be blocked and say so in the design note. The sibling projectile skill documents the same rule for its Area3D hit detection; the fix is the same call.
5. Run all interception logic in `_physics_process`, never in `_process` or an input callback. Area signals fire on the physics tick; resolving them on the render tick desyncs the outcome from the arrow's position by up to a frame, which is exactly the window a fast arrow needs to pass through.

**Check**
- With the guard held and an arrow fired from range: the `area_entered` signal fires exactly once, before the arrow reaches the player body. With the guard down: no signal, the arrow hits the player. With an unblockable arrow and the guard held: no interception, the arrow hits the player.
- An arrow fired from point-blank range with the guard already held is resolved by the overlap query in step 4, or the design note records that it is not. If it sometimes blocks and sometimes does not, the overlap query is missing.
- The volume sees arrows only. If it fires for the player's own sword, a friendly projectile, or the ground, the mask is wrong; fix the mask, not the signal handler.

**Why**
- The creator's original bug was a collision accident: a blocking volume that stopped everything, including arrows, because it was a physical blocker. The guard volume must be the opposite: a sensor that sees one thing, decides one outcome, and never physically blocks anything. The layer mask is the entire mechanism; a mask that sees the world turns the guard into a wall, which is the bug the thread started from.

## Phase 3: The timing state machine (parry lives here, block does not need it)

**Do**
1. Model the guard as three states with explicit timers, all in seconds, all exported tuning values labeled as this skill's starting points (the thread gives no numbers): IDLE (guard down), ACTIVE (the parry window, starting point 0.20 s, the Sekiro base window below), RECOVERY (starting point 0.35 s, during which a new press does nothing). Holding the guard without a fresh press is the block outcome from the pick list, not a parry: it uses the Phase 2 volume with no timing at all.
2. Start the ACTIVE window on a fresh press, not on holding the button. A press that lands while already ACTIVE restarts nothing; a press during RECOVERY is ignored. The window is measured from the press to the arrow's entry into the volume, not from the press to the arrow's launch: the only moment that matters is contact.
3. Add the spam penalty, recommended, from the shipped reference below: each press inside a short grace period after the previous press (starting point 0.5 s, matching Sekiro's 30-frame reset) shrinks the next ACTIVE window (starting points: 0.20 s, then 0.10 s, then 0.07 s), and a successful parry restores the full window immediately. Without the penalty, mashing the guard key is the optimal strategy and timing stops meaning anything. With it, flurries still work (each success resets the penalty), which is the same exception Sekiro makes.
4. Gate the parry behind the ACTIVE state only. An arrow entering the volume during ACTIVE is a parry; during a held guard with no fresh press it is a block; during RECOVERY it hits the player. There is no fourth case. If the design adds a stamina cost (David Bingham's unendorsed proposal), it is deducted on entering ACTIVE, not on a successful parry, so a mistimed press costs something and a held guard costs nothing extra.
5. Record every parry in a debug counter (attempts, successes, successes inside the last 0.05 s of the window). Tune the window from the counter, not from feel: if successes cluster at the window's end, the window is too generous; if attempts never succeed, it is too tight or the volume is too small.

**Check**
- A press 0.10 s before impact parries; a press 0.30 s before impact blocks (held guard) or is hit (if released into RECOVERY). A held guard never parries, no matter how long it is held. Three rapid presses shrink the third window; a successful parry restores the full window on the next press.
- The counter shows the distribution. If every attempt succeeds, the window is a block in disguise; if none succeed, the volume or the window is broken, not the player.

**Why**
- A parry is a purchase, not a reflex test: the player buys a better outcome with timing, and the price must be real (a window that ends, a recovery that punishes mashing). The thread's own evidence supports this: the creator called the original block "awkward" and conceded dodging was probably easier, which means the held-guard version was not worth using. The timing window plus the stronger redirect is what makes the defensive option worth choosing over a dodge.

## Phase 4: The three outcomes (bounce, catch, slash)

**Do**
1. **Bounce (the verdict).** On interception during a held guard or a parry, compute the redirect from the arrow's incoming velocity and the guard's facing normal: `new_velocity = velocity.bounce(normal)`, where `bounce` returns the vector "bounced off" a plane defined by the normal (the reflection `v' = v - 2(v·n)n`). Use the guard plane's normal (the sword blade's facing direction, or the player's forward direction for a body block), not the arrow's own orientation: an arrow arriving at a shallow angle should glance off, not reverse. For a block, keep the speed and add a small upward bias so the arrow drops to the ground instead of flying back into the archer's face at full speed; for a parry, keep or slightly increase the speed and aim the reflection back along the arrow's incoming line, so a parried arrow can hit its shooter. Both speed treatments are this skill's design; the thread decided "bounce off with sparks" and nothing about speed or direction. Hand the redirected velocity back to the arrow's flight script (the sibling projectile skill's flight ownership rule: one script owns the transform; the deflection writes a new velocity into it, it does not teleport the arrow). Mark the arrow as deflected so it cannot be deflected twice and so it no longer targets the player.
2. **Catch (endorsed proposal, never shown).** On interception during a dedicated catch input (a grab press, not the guard), freeze the arrow: stop its flight script, attach it to the hand node, play a grab snap, and after a short hold convert it into ammunition (increment the arrow count) or despawn it. The catch input must be distinct from the guard input; if the same button does both, the catch outcome is unreachable in practice and the feature is dead code. The catch window uses the Phase 3 ACTIVE timing. No thread evidence says what a caught arrow becomes; the ammunition conversion is this skill's recommendation, following Robert Aultman's unendorsed ammo-reuse proposal, and it must be labeled as such in the design note.
3. **Slash (endorsed proposal, never shown).** On an attack swing, the swing's hitbox is an Area3D active only during the swing's active frames (the same area-entered pattern as Phase 2, with the swing's animation driving the enable window). An arrow entering during active frames is cut: despawn the arrow and spawn the two-half visual (two short rigid bodies or two mesh halves with an initial split velocity and a short lifetime, falling to the ground), plus the Phase 5 spark burst. The halves are visual only; they deal no damage and cannot be deflected again. The slice-in-half visual is Greyson Loomis's unendorsed proposal; the cut itself is the creator-endorsed slash. Keep the two attributions separate.
4. **Unblockable arrows pass through.** Any arrow with `is_deflectable == false` ignores all three outcomes. Give it a distinct visual read before it arrives (a color, a glow, a trail) so the player can tell it apart from a deflectable arrow at a glance; the shipped references below use exactly this language (red glints, perilous markers). An unblockable arrow that looks identical to a blockable one is a broken promise, not a difficulty feature.

**Check**
- Bounce: an arrow fired straight at a held guard rebounds along the reflection of its incoming line and lands on the ground in front of the player; a parried arrow returns toward the shooter. A shallow-angle arrow glances sideways instead of reversing. No arrow is deflected twice.
- Catch: the grab input freezes the arrow at the hand and the ammunition count rises by one (or the design note records the other conversion). The guard input never catches.
- Slash: an arrow crossing the swing's active frames splits and falls; an arrow crossing before or after the active frames hits the player normally. The halves never damage anything.
- Unblockable: the marked arrow passes through the guard, the catch, and the swing, and hits the player. An unmarked arrow never does.

**Why**
- The redirect math is the only part of this system that must be exact: a wrong normal makes arrows fly sideways on head-on blocks, which reads as a bug even when the timing was perfect. `bounce` against the guard plane's normal is the whole computation; everything else in this phase is state management around it. The three outcomes share one interception and differ only in what happens after it, which is why they share one volume and one timing machine instead of three separate systems.

## Phase 5: Feedback (the spark, the ting, the freeze)

**Do**
1. Fire the spark burst on every interception, at the contact point, oriented along the guard normal. Use a `GPUParticles3D` with `one_shot = true` and `explosiveness = 1.0` (all particles emitted simultaneously), `amount` set to the burst size, and a `ParticleProcessMaterial` with `direction` set to the guard normal and a spread cone. Parent the burst to the scene root, never to the arrow or the player: the burst must outlive the arrow it came from. Restart it with `restart()`, not by setting `emitting = true`: for one-shot emitters the docs warn that setting `emitting` will not restart the cycle until all active particles finish, and `restart()` avoids the delay. The burst is the Oct 25 verdict made visible ("bounce off with sparks"); a bounce with no burst reads as a miss.
2. Play the ting on every interception: a short metallic sound, higher pitched and louder for a parry than for a block. The shipped references agree on this point: Sekiro's deflect has a distinct, higher-pitched clang, and audio is the more reliable teacher than the visual spark. Two layers (a base metallic hit plus a bright overtone for parries) is enough; pitch wobble per hit stops it sounding mechanical.
3. Add hit-stop on parries only, never on blocks. Drop `Engine.time_scale` to 0.05 for a short real-time duration (starting point 0.06 s for a parry, 0.12 s for a parry that kills or staggers), then restore it with a timer that ignores time scale: `get_tree().create_timer(duration, true, false, true)` (the fourth argument is `ignore_time_scale`). A normal timer slows down with the game and the freeze lasts over a second; the docs and the working examples agree the restore timer must count real time. Never set `Engine.time_scale` to 0.0: code that never expects a zero delta breaks, and the docs recommend a value greater than zero. If a slow-motion ability (Phase 7) is also running, the hit-stop must not restore the scale to 1.0 over it: use a smallest-scale-wins controller or an ownership counter so only the newest effect restores, and the slow motion resumes after the freeze.
4. Show the archer reacting on a parry: a flinch, a step back, or a pause before the next shot. The thread's own evidence for why this matters is the archer-panic proposal ("If you do 3 in a row make the archer start panicking and stop firing"), which was never endorsed but names the right feedback channel: the enemy's behavior is the readable consequence of the player's timing. A parry that changes nothing about the archer is a sound effect, not a mechanic. The reaction is this skill's design; the thread decided the bounce, not the archer's response.
5. Keep block feedback smaller than parry feedback on every channel at once: fewer spark particles, a duller sound, no hit-stop, no archer reaction. If a block looks and sounds like a parry, players cannot learn the difference, and the timing system has no teacher.

**Check**
- Every interception shows a burst at the contact point that keeps playing after the arrow is gone; every parry adds the higher ting and a brief freeze that ends on time; a block shows the smaller burst and no freeze. Two parries in quick succession do not leave the game stuck in slow motion and do not restore full speed over a running slow-mo.
- The archer visibly reacts to a parry within one beat of the interception. If nothing about the archer changes, the feedback phase is unfinished.

**Why**
- The creator's own complaint about the original block was feel: "yes right now it feels awkward". Feel is not a mystery ingredient; it is these three channels firing together on the same frame (burst, ting, freeze) with the parry's version strictly bigger than the block's. The hidden-mechanic decision in Phase 6 makes this load-bearing: with no tutorial, the feedback is the only teacher, so it must be unambiguous on first contact.

## Phase 6: Keep it hidden, but make it discoverable

**Do**
1. Honor the Oct 25 decision literally: no tutorial prompt, no tooltip, no loading-screen tip, no skill-tree entry, no control remap label that names arrow deflection. The mechanic is not listed anywhere the player reads before playing.
2. Make discovery possible in normal play, in this order: first, an archer fires at a player who happens to be holding guard, and the bounce plus sparks happen (the player sees the outcome without trying); second, the ting and burst are distinctive enough to be recognized on repeat; third, the parry's stronger feedback (bigger burst, higher ting, hit-stop, archer reaction) marks the timed version as a better version of the same thing, which invites experimentation. If any step requires the player to already know the mechanic, discovery is broken.
3. Never gate progression on the hidden mechanic. No boss, door, or required encounter may demand a parry, catch, or slash to proceed. The hidden mechanic is an advantage for players who find it, never a key. This is the cost of the creator's decision, and it is non-negotiable: a required hidden mechanic is a softlock wearing a discovery fantasy.
4. Let the community be the second teacher, the way the thread itself was. The creator's own design process was public (reels, votes, replies); the skill's discovery design assumes the same: players who find it will show it to others. Do not patch the mechanic out of patch notes either; a patch note that names it ends the hidden period, which is a separate decision for the creator, not a default.

**Check**
- A fresh player holding guard against the first archer sees a bounce with sparks and a ting within the first encounter, without reading anything. A player who never holds guard still finishes the game. Both statements must be true at once; if either fails, the hidden design is wrong in opposite directions.
- No tutorial text, tooltip, or menu entry names the mechanic. Search the string tables for "deflect", "parry", and "block arrow": the only hits are internal identifiers, never player-facing text.

**Why**
- The lineage for this decision is older than this thread: Street Fighter II's combos were an accident a developer chose to leave in as a hidden trick, Super Smash Bros. Melee's wavedash was found in testing and deliberately kept, and Street Fighter III's red parry went unnoticed by most players for five years. Hidden mechanics survive when they are discoverable by accident and rewarding on purpose; they die when they are required or when they are invisible. The creator's "dont officially let the player know" is the first half of that lineage. This phase is the second half.

## Phase 7: The slow-motion variant (the Jul 11 origin, proposed, not shipped)

**Do**
1. Treat this phase as a second feature, not part of the first build. Its entire content is endorsed proposals from Jul 11 plus unendorsed tuning ideas; nothing here was shown working in any reel. Build it only after Phases 2 through 5 are verified.
2. Implement the slow motion as a timed window, per the creator-endorsed "great idea!": on the ability input, drop `Engine.time_scale` to a slow value (starting point 0.3) for a fixed real-time duration (starting point 1.5 s; urbud.'s unendorsed tuning: 1-2 s for skill-oriented play, longer for a badass feel). The restore timer must ignore time scale (Phase 5, step 3). During the window, the Phase 2 guard volume and Phase 3 timing still apply; the slow motion makes the timing easier to hit, which is the whole point of pairing them.
3. Add the meter only if the design wants a cost: a recharge meter that fills over time and, per The Sandwich's unendorsed proposal, fills faster on near misses, incentivizing risky play when the meter is low. The meter is a separate tuning surface from the timer; do not ship both a timer and a meter deciding the same window. Pick one: the creator endorsed the timer ("great idea!"); the meter was never endorsed.
4. Keep catch and slash available during the window with the same inputs as outside it. The Jul 11 proposals were specifically about slow-motion catching and slashing ("slash or catch the arrows in slomo"), so the window exists to make those two outcomes reachable. If catch and slash are not built, the slow-motion window has no reason to exist for this system.

**Check**
- The window lasts the tuned real-time duration and restores full speed exactly once, even if a hit-stop fires inside it. Catch and slash both work inside the window with their normal inputs. The meter, if built, fills on near misses and never exceeds its cap.
- The slow motion never triggers from the guard input alone. If it does, the ability input and the guard input are conflated, and the window will fire every time the player blocks.

**Why**
- Slow motion is a difficulty decision disguised as a feel feature (Ayda's unendorsed framing in the thread: perfect timing versus remove, depending on whether the knight should be a badass or on equal footing). Pairing it with the timing window lets the game be generous exactly where the thread's proposals are hardest (mid-flight catches), without making the base block easier. That is the only justification for the extra system; without catch and slash, it is spectacle in search of a mechanic.

## The human method, distilled

1. **The thread is the spec.** Dated verdicts are requirements; liked comments are not. Keep the two lists separate or the build overreaches.
2. **A bug is a mechanic candidate, not a mechanic.** The invisible wall became a feature only after a vote, a verdict (bounce with sparks), and a decision about discoverability. Any one of those missing leaves a bug.
3. **One volume, one timing machine, three outcomes.** Block, parry, catch, and slash share the interception; they differ only in what happens after it. Separate systems for each outcome duplicate the hardest part (the volume) four times.
4. **Feedback is the tutorial.** With no tutorial text, the burst, the ting, and the freeze must teach the difference between block and parry on first contact. If they do not, the hidden mechanic is undiscoverable, not mysterious.
5. **The redirect math is exact; the rest is tuning.** `bounce` against the guard normal is the computation. Window lengths, speeds, and costs are starting points to be measured, never quoted as the creator's numbers.
6. **Hidden means optional.** A mechanic nobody is told about must never gate progression. The moment it is required, it stops being hidden and starts being a softlock.

## Failure modes

- **The guard volume is a physical blocker.** The mask includes the world or the player, so the volume stops arrows by collision instead of by decision, and it stops everything else too. That is the original bug. Fix: mask to the projectile layer only, sensor semantics only (Phase 2).
- **Point-blank arrows never block.** The arrow spawns inside the volume and no transition fires. Fix: the overlap query on enable (Phase 2, step 4), or record the limitation.
- **Mashing beats timing.** No spam penalty, so the optimal play is hammering the guard key. Fix: the shrinking window with reset on success (Phase 3, step 3).
- **Held guard parries.** The parry check reads "guard is up" instead of "fresh press inside the window". Fix: the state machine distinguishes held from pressed; a held guard is a block, always (Phase 3).
- **Double deflection.** The arrow is bounced, then bounces again off the same volume or a second volume. Fix: the deflected flag; a deflected arrow is inert to all guard volumes (Phase 4).
- **The burst dies with the arrow.** A one-shot burst parented to the projectile is freed with it, or `emitting = true` fails to restart it. Fix: parent bursts to the scene root, restart with `restart()` (Phase 5).
- **Hit-stop never ends, or ends the slow motion.** The restore timer counts scaled time, or it restores to 1.0 over a running slow-mo. Fix: real-time timer, smallest-scale-wins ownership (Phase 5, step 3).
- **Shallow arrows reverse.** The reflection uses the arrow's orientation instead of the guard normal. Fix: `bounce` against the guard plane's normal (Phase 4).
- **Unblockable arrows look blockable.** No visual distinction, so the player reads a correct parry as a failed input. Fix: the distinct read before arrival (Phase 4, step 4).
- **The slash fires outside active frames.** The swing hitbox stays enabled through the whole animation, so arrows are cut during windup and recovery. Fix: enable the hitbox only during active frames, driven by the animation (Phase 4, step 3).
- **The hidden mechanic gates progression.** A required encounter demands a parry. Fix: remove the requirement; hidden mechanics are advantages, never keys (Phase 6, step 3).
- **The bounce was never shown working.** The Oct 29 reel asserts the fix; no frame shows a bounce. Do not present the bounce as shipped creator behavior. This skill implements the documented decision; verification is the Phase 4 checks, not the reel.

## AAA studio practice

- **FromSoftware, Sekiro: Shadows Die Twice (2019).** The timing-window reference. Base deflect window 12 frames (0.2 seconds) before impact; the window shrinks with each recent guard release, to as little as 4 frames, and spamming is explicitly not recommended; the penalty resets after 30 frames and immediately after a successful deflect. Pressing early yields an ordinary guard instead of a deflect, and a successful deflect deals significant posture damage with a distinct sound and spark. Perilous attacks cannot be deflected at all. Source (read firsthand): Fextralife, "Deflection", https://sekiroshadowsdietwice.wiki.fextralife.com/Deflection . The Phase 3 state machine and spam penalty are modeled on this, with the numbers labeled as Sekiro's, not the creator's.
- **Sucker Punch, Ghost of Tsushima (2020).** The arrow-specific reference. A perfect parry is a tap just before the weapon lands (react to the weapon's forward motion, not the windup), rewarded with slow motion and a counterattack; holding block only blocks. Arrows are a separate, locked case: they can be parried only with the Deflect Arrows technique, and the perfect parry cannot be used against them without it. Charms widen the parry and dodge windows (Charm of Mizu-no-Kami, Charm of Kagu-Tsuchi). Source (read firsthand): ScreenRant, "Ghost of Tsushima: How To Perfect Parry Enemy Attacks", https://ScreenRant.com/ghost-tsushima-perfect-parry-easy-guide/ ; Neoseeker, "Combat Basics", https://www.neoseeker.com/ghost-of-tsushima/Combat_Basics . The lesson for this skill: arrows deserve their own rule and their own unlock language, and window-widening is a legitimate progression reward, which is the honest version of David Bingham's unendorsed progression-gating proposal.
- **The hidden-mechanic lineage.** Street Fighter II's combos began as an accident (a coder let moves interrupt hit stun) that the lead developer deliberately left in as a hidden trick; Super Smash Bros. Melee's wavedash was found in testing and deliberately kept; Street Fighter III's red parry went unnoticed by most players for five years. Sources (read firsthand): Smashboards, "Project M Social Thread" history lesson, https://smashboards.com/threads/project-m-social-thread.260812/page-632 ; ScreenRant, "17 Things You Didn't Know You Could Do In Street Fighter", https://screenrant.com/street-fighter-tips-hints-tricks/ ; NeoGAF, "Game mechanics that you didn't even know about", https://www.neogaf.com/threads/game-mechanics-that-you-didnt-even-know-about.1118302/page-4 . The lineage supports Phase 6: hidden mechanics are discovered by accident, kept on purpose, and rewarding on purpose, and they are never required.
- **Godot game-feel practice (hit-stop).** Drop `Engine.time_scale` to 0.05, restore with a timer that ignores time scale, never use 0.0, and give overlapping hit-stops an owner so only the newest restores. Sources (read firsthand): UhiyamaLab, "Godot Hitstop Basics", https://uhiyama-lab.com/en/notes/godot/hit-feedback-hitstop/ ; Godot Forum, "Game feel checklist for Godot 4", https://forum.godotengine.org/t/game-feel-checklist-for-godot-4-hit-stop-trauma-shake-coyote-time-and-more/145340 .

## Agent automation

- **Verdict gate.** A design-note check fails the build when any unendorsed proposal appears in the "decided" list, or when a creator verdict is quoted without its date. The verdict list is data: each entry carries the quote, the author, the date, and the raw JSON path it was verified in.
- **Volume gate.** A headless test scene fires one arrow per case: guard held blocks, guard down hits, unblockable passes through, point-blank resolves via the overlap query. Any case failing fails the build. The mask under test is recorded; a mask edit re-runs this gate.
- **Timing gate.** Scripted presses at fixed offsets before impact: 0.10 s parries, 0.30 s blocks-or-is-hit, held guard never parries, three rapid presses shrink the third window, a success restores the full window. A press that parries outside its window is a fail.
- **Redirect gate.** Arrows fired head-on, at 45 degrees, and at a shallow angle against the guard: each must rebound along the reflection of its incoming line against the guard normal, within a recorded tolerance, and no arrow may be deflected twice. A rebound that reverses a shallow arrow is a fail.
- **Feedback gate.** Every interception in the test scene must produce exactly one burst at the contact point and one sound event; every parry must produce a hit-stop that ends within the tuned duration and restores the prior time scale. A burst parented to the arrow, or a hit-stop that outlives its timer, is a fail.
- **Hidden-mechanic gate.** A string-table scan fails when "deflect", "parry", or "block arrow" appears in any player-facing text. A progression-dependency scan fails when any required encounter lists a parry, catch, or slash as its solution.
- **Slow-mo gate.** The Phase 7 window is tested separately from the base system: duration in real time, single restore, hit-stop inside the window does not end the slow motion, and the ability input never fires from the guard input.

## Valkyrie note

Fit is partial, and the split is clean. What transfers: the timing-window state machine, the redirect math, and the feedback stack (burst, ting, hit-stop) are engine-agnostic and map directly onto citizen combat: citizens already act on the sim's deterministic tick, so ACTIVE and RECOVERY windows are exact frame counts, not wall-clock guesses, and a parried arrow redirecting back toward its shooter is a readable iso-camera moment. The god-hand transfer is the second one: a player-drawn guard or intervention zone that deflects projectiles uses the same volume-plus-timing shape, with the cursor replacing the sword. What does not transfer: the first-person sword-block staging (Valkyrie's fixed iso camera never sees a blade fill the frame, so the guard volume must be visible as a citizen pose plus a readable effect, not as a viewmodel), and the hidden-mechanic decision needs care at crowd scale (a hidden option one citizen in a hundred can use is invisible; if it ships in Valkyrie, the discovery path must be a visible citizen behavior, not a first-person accident). Do not import the first-person specifics; import the state machine, the math, and the feedback.
